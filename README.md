## 亮点

|  | |
| --- | --- |
| **两个站点** | Netflix 与 Prime Video，共用同一套主循环和评分来源 |
| **两个评分并排** | 豆瓣在前（绿），IMDb 在后（IMDb 自己的金黄色），一眼分得清哪个是哪家 |
| **两边各自独立** | 豆瓣被限流时 IMDb 照常出分，反之亦然；任一来源都能单独关掉 |
| **点哪段跳哪家** | 点绿色去豆瓣条目，点黄色去 IMDb 条目，都不会误触发 Netflix 的播放 |
| **界面语言无所谓** | 英文原名、简体译名、繁体台译都能命中。IMDb 那边尤其绕——它认得中文片名却只回英文标题，为此单独做了跨语种匹配 |
| **点开过的片优先出分** | 点击是最强的兴趣信号，会插队，并重查一次早先的「未收录」 |
| **宁可不显示，也不显示错的分数** | 匹配不够可信时留空，而不是给一个看起来对的错分 |

## 安装

目前是开发版，需要自行构建：

```bash
npm install
npm run build
```

然后在 Chrome 打开 `chrome://extensions` → 打开右上角的**开发者模式** → 点**「加载已解压的扩展程序」** → 选择项目下的 `dist` 目录。

> **改代码后要三步**：`npm run build` → 在 `chrome://extensions` 点该扩展的 🔄 刷新 → 刷新 Netflix / Prime Video 页面。少做一步和「代码有 bug」的表现完全一样，参见下方「先确认跑的是哪一版」。

## 设置

点浏览器工具栏上的扩展图标：

| 设置 | 说明 |
| --- | --- |
| 启用扩展 | 总开关。关掉后立即清除页面上所有角标 |
| 在 Netflix 上启用 | 关掉即不在 Netflix 上注入任何东西 |
| 在 Prime Video 上启用 | 同上 |
| 显示豆瓣评分 | 关掉即不再向豆瓣发任何请求 |
| 显示 IMDb 评分 | 关掉即不再向 IMDb 发任何请求 |
| 在列表封面上显示 | 关掉则只在详情弹层里显示 |
| 在详情弹层中显示 | 悬停卡片弹出的详情层 |
| 未收录时也占位 | 默认关闭，列表页留白更干净 |
| 角标位置 | 封面的四个角任选 |
| 清空评分缓存 | 想强制重新查询时用，两个来源一起清 |

弹窗底部会分来源显示已缓存的条数、已记录的「关注」部数；被限流时变成橙色提示并给出恢复时间。

## 使用体验：四个预期

**首次浏览新页面时，会有一部分卡片没有评分。** 这不是 bug，是刻意的取舍：扩展以匿名方式访问两个站点（不携带 cookie，见「隐私」），而豆瓣对匿名请求的配额很紧。所以请求经过严格限速，只为你真正停下来看的卡片查询。**已查到的会缓存 7 天，常看的内容会越来越全。**

**两个来源的出分节奏不一样。** 豆瓣间隔 2.5 秒，IMDb 宽松得多（0.6 秒），所以经常是 IMDb 先出、豆瓣随后补上。一张封面上先只有黄色那段是正常的。

**评分是陆续出现的，不是一次性刷出来。** 视口里的卡片按从上到下、从左到右排队查询。

**想先看哪部，点它一下。** 点开卡片就是在告诉扩展「我对这部感兴趣」：它的查询会插到队首；如果之前显示的是「未收录」，还会重查一次——那多半只是当时被限流了。同一部片半小时内只重查一次，连点几下不会多花配额。记录只存本地（最多 200 部）。

## 遇到问题

| 现象 | 怎么办 |
| --- | --- |
| 完全没有角标 | **先分清是哪一种**：Console 里执行 `document.documentElement.dataset.dbrLoaded`。有值 = 脚本注入了，去看有没有「没有找到任何影片卡片」的警告（那是选择器失效）；**是 `undefined` = 脚本根本没注入**，见下方「脚本没注入」 |
| 只有少数片有评分 | 正常，见上方「四个预期」。等缓存积累 |
| 角标里出现奇怪的文字 | 多半是别的扩展（如翻译类）在改 DOM，见「和其它扩展共存」 |
| 评分明显配错了片 | 这是真 bug。点扩展图标 →「检索接口诊断」→ 用「单片排查」输入片名，把输出发给开发者 |
| 弹窗显示橙色限流提示 | 等提示里给出的时间，期间扩展会自动停止请求 |

**脚本没注入（`dbrLoaded` 是 `undefined`）。** 这和「选择器失效」是两回事，页面上没有任何线索能区分——脚本没跑起来的话，连那条 Console 警告都不会有。按这个顺序查：

1. **换个站点试。** 在 Netflix 上也执行一次 `document.documentElement.dataset.dbrLoaded`。Netflix 有值而这个站点没有 → 是 manifest 的匹配规则没覆盖当前域名；两个都没有 → 扩展本身没加载或没重新构建。
2. **看当前 URL。** Prime Video 的投放形态有两类：独立站点 `primevideo.com`，以及各区域 amazon 站点下的 `/gp/video/` 路径。manifest 里两类都写了，但 amazon 的域名是逐个列举的（`.com` / `.co.jp` / `.de` …），你所在的区域站可能不在名单里。把 URL 发回来，或者直接往 `manifest.json` 的 `content_scripts` 里加一行。
3. **注意裸域名。** `https://www.primevideo.com/*` 这样的写法**匹配不到**不带 `www` 的 `primevideo.com`——必须写成 `https://*.primevideo.com/*`。这个坑已经踩过一次，现在有 `tests/manifest.test.ts` 守着。

**先确认跑的是哪一版。** `npm run build` 会打印一个版本戳，内容脚本把同一个戳写在 `<html data-dbr-loaded>` 上。在 Netflix 或 Prime Video 页面的 Console 里执行 `document.documentElement.dataset.dbrLoaded`，两者一致才说明新代码真的生效了。

想看详细日志：Console 里执行 `localStorage.setItem('dbr:debug', '1')` 后刷新页面。

## 隐私

扩展只做两件涉及网络的事：把影片标题发给豆瓣和 IMDb 做检索、取回评分。没有任何数据上报到第三方，评分缓存只存在浏览器本地的 `chrome.storage.local` 里。

**「点击过哪些片」也只存在本地。** 记录的是归一化后的标题和一个时间戳，最多 200 条，只用来决定查询的先后顺序，不随请求发出、也不上传到任何地方。关掉总开关即不再记录。

**两个来源的请求都不携带 cookie（`credentials: 'omit'`），这是一个明确权衡后的选择。** 带上浏览器里的豆瓣 cookie（哪怕只是访问过豆瓣被种下的匿名 bid，无需登录）能与正常浏览共享宽松得多的配额，同类插件多数如此；但那等于让扩展以用户身份访问豆瓣。这里选择保持匿名，代价是配额紧、首次浏览新页面时会有相当一部分卡片没有评分。

权限只申请了 `storage`（存设置和缓存），以及取数所需的五个域名：`search.douban.com`、`movie.douban.com`、`v3.sg.media-imdb.com`、`v2.sg.media-imdb.com`、`api.graphql.imdb.com`。没有申请任何与取数无关的权限。

## 已知限制

- **不能公开分发。** IMDb 的 GraphQL 响应附带使用条款，禁止公开/商业使用，详见下方「使用条款」。自用没问题，上架需要另换数据源。
- 匿名请求的配额很紧，首次浏览新页面时会有相当一部分卡片没有评分，需要靠缓存逐步积累。这是「不携带 cookie」这一隐私选择的直接代价。
- 列表卡片上拿不到年份时，匹配走收紧后的阈值（88 分）；详情弹层能提供年份，阈值放宽到 70。
- 冷门片、Netflix 独占的小语种内容可能两边都查不到，此时列表页留空、详情页显示「未收录」。
- 繁简转换用的是一份覆盖影视标题高频字的精简表（见 `src/shared/text.ts`），不是完整的 OpenCC。缺字只会导致匹配不上，不会匹配错。
- 剧集按季匹配：查询没有指明季数时默认取第一季。IMDb 一部剧只有一个条目，不按季拆。
- Prime Video 的选择器已按实测结构收敛，但只在一个区域站、一种页面布局上验证过。换区域或改版后若失效，跑 `scripts/dom-probe.js` 把报告贴回来即可重新收敛。
- Prime Video 目前只接了 `primevideo.com`，amazon 各区域站下的 `/gp/video/` 路径还没接（往 manifest 的 `content_scripts` 里加一行即可）。

# 技术细节

## 它是怎么工作的

```
内容脚本 (Netflix 页面内)              background service worker
┌────────────────────────────┐        ┌────────────────────────────────┐
│ MutationObserver           │        │ RatingLookup ×2                │
│   发现新出现的影片卡片      │        │   缓存 / 去重 / 优先级的编排    │
│ IntersectionObserver       │        │   对数据来源无知                │
│   只为进入视口的卡片查询    │──消息─→│     ├─ DoubanProvider          │
│ badge                      │←──────│     │    queue 2.5s · cache r3: │
│   一个角标里并排多个来源    │        │     └─ ImdbProvider            │
│   各段独立渲染、独立跳转    │        │          queue 0.6s · cache i1:│
└────────────────────────────┘        │ matcher                        │
                                      │   候选打分，不够可信就不显示    │
                                      │ InterestStore                  │
                                      │   点过的片 → 高优先级           │
                                      └────────────────────────────────┘
```

**两个来源各持一条独立的队列和缓存。** 这不是洁癖：两边的限流各自独立，共用一条队列意味着豆瓣退避时 IMDb 也停摆——而豆瓣的匿名配额恰恰是最容易打穿的那个。分开之后，最坏情况只是少一半分数，而不是整个角标消失。

<details>
<summary><b>豆瓣的取数路径</b>（两级检索、软限流识别、为什么不解析条目页）</summary>

**豆瓣没有公开 API。** 官方 API v2 早已停发 key，走的是豆瓣站内在用的两个检索入口，主备关系（均实测）：

- **主：`movie.douban.com/j/subject_suggest`。** 轻（几百字节）、带年份和原名（`sub_title` 存原始语言标题）、简体和英文都能查。它的限流表现是**返回空数组而不是报错**——这曾让我们误判它「彻底废了」而整个切走，其实它只是当时被限流了。繁体查不到，靠上层先做繁转简。
- **备：`search.douban.com/movie/subject_search`。** 解析结果页内嵌的 `window.__DATA__`。召回宽得多（会搜「又名」，港台译名靠它）且自带评分，但对无 cookie 访问的限流极严，几次就触发软限流：**HTTP 200 + `error_info:"搜索访问太频繁。"` + items 为空**。这个形态曾被当成有效的空结果缓存成「未收录」，导致整页所有片子（包括《绝命毒师》）显示未收录——所以 `error_info` 非空必须按限流处理，绝不能当成「豆瓣没这部片」。该接口只在 suggest 拿不到可信匹配时才出场，软限流后自我静默 5 分钟且不牵连 suggest。

suggest 不带评分，命中后由 `subject_abstract` 补一次；完整搜索的结果自带评分则免掉这一步。这些接口都没有契约保证，解析一律「宽进严出」；切 `__DATA__` 用括号配对扫描而不是正则。

**不解析条目页 HTML。** 曾打算拿 `movie.douban.com/subject/<id>/` 做取分兜底，实测第一次请求就被重定向到 `sec.douban.com` 的风控页。这条路不但取不到分，还会白白把请求队列打进退避、连累后续正常请求，所以整个移除了。搜索结果页反而不受这个限制。

**界面语言用哪种都行。** 搜索结果的标题常常是「中文名 原名」拼在一起（`星河战队 Starship Troopers`），解析时会拆成两个名字分别参与匹配——不拆的话英文查询只能算「包含关系」，分数过不了无年份时的阈值。

</details>

<details>
<summary><b>IMDb 的取数路径</b>（实测结论、跨语种匹配、使用条款）</summary>

**IMDb 同样没有面向第三方的免费 API**——官方 API 要钱，OMDb 要用户自己注册 key。所以走的是 imdb.com 自己在用的接口，和豆瓣同一个性质：没有契约保证。

以下全部来自实测，不是推测。

### 检索：`v3.sg /suggestion/x/`（备用 `v2.sg /suggestion/t/`）

| 入口 | 英文 | 简体 | 繁体 |
| --- | :-: | :-: | :-: |
| `v3.sg /suggestion/x/` | ✅ | ✅ | ✅ |
| `v2.sg /suggestion/t/` | ✅ | ✅ | ✅ |
| `/suggestion/{首字母}/` 变体 | ✅ | ❌ 404 | ❌ 404 |
| 老版 JSONP `/suggests/` | ✅ | ❌ 404 | ❌ 404 |

**中文查询直接可用**，不需要先把片名翻成英文。返回字段 `i, id, l, q, qid, rank, s, tl, y, yr`。`tl` 是展示用副标题（`"2008-2013 TV Series"`），不是本地化标题，解析里没用它。响应里混着人名（`nm` 开头）和系列条目（`in` 开头），只取 `tt` 开头的。

### 取分：`api.graphql.imdb.com`，且必须带三个自定义头

```
x-imdb-client-name: imdb-web-next
x-imdb-user-country: US
x-imdb-user-language: en-US
```

同一个地址、同一个查询的三种打法，结果泾渭分明：

| 打法 | 结果 |
| --- | --- |
| 裸 POST | ❌ 403（nginx 的 403 页面） |
| 改用 GET | ❌ 403 |
| POST + 上面三个头 | ✅ 200 · 444 字节 · `{"aggregateRating":9.5,"voteCount":2668078}` |

关键在于这三个都是**自定义头**，扩展设得了。`Origin` 和 `Referer` 是 Fetch 规范里的禁止修改头，扩展设了会被浏览器忽略——所幸实测证明不需要它们。

**条目页兜底已移除。** `www.imdb.com/title/…` 在浏览器里同样只返回 1997 字节的反爬拦截页（正文明确含 `enable javascript` 和 `challenge`），`/find` 对四个完全不同的查询词返回一模一样的字节数。留着它意味着每次失败都白下一次 2KB、还要报一条误导性的「页面里没有评分数据」——那句话会把下次排查引向解析逻辑，而真实原因完全不在那儿。和当初移除豆瓣条目页兜底是同一个判断。相应地 `host_permissions` 里也去掉了 `www.imdb.com` 和 `m.imdb.com`——角标跳转只是普通链接，不需要权限。

### 中文界面下的匹配：IMDb 用中文能搜到，但只回英文标题

这是实测暴露出的、会让功能对中文用户完全失效的一点。查「鱿鱼游戏」，IMDb 返回的是：

```json
{"id":"tt10919420","l":"Squid Game","qid":"tvSeries","y":2021}
```

拿「鱿鱼游戏」和「Squid Game」算字面相似度是 0 分，通用匹配器会把它整个扔掉——**搜索成功了，评分却被自己丢了**。

所以 IMDb 有一套自己的匹配（`src/background/imdb/match.ts`），在通用打分拿不到结果时启用跨语种回退，依据换成「IMDb 自己的检索排序」。它认得中文别名，命中就排第一。但这个信号比字面匹配弱，所以卡得很紧：

- **只认第一名。** 排在后面的是同系列衍生作品——「Breaking Bad」那次返回 8 条，第三条是《续命之徒》，配上去就是错的。
- **类型必须相容**，电影不能配到剧集上。
- **有年份就必须对得上**（容 1 年）。详情弹层里能拿到年份，那是最有力的旁证。
- **字面本来可比时不启用**：两边都是拉丁字母却没匹配上，那就是真的没匹配上，不该靠「排第一」硬塞。

另外 IMDb 一部剧只有一个条目、不按季拆（豆瓣按季拆），所以匹配前会先去掉季数后缀，否则通用匹配器的季数罚分会误伤。

### ⚠️ 使用条款

GraphQL 的响应里 IMDb 附带了一句声明：

> Public, commercial, and/or non-private use of the IMDb data provided by this API is not allowed.

自用没问题，**但如果打算上架 Chrome Web Store 分发，这条会是障碍**。真要公开分发，得换成有明确授权的数据源（比如需要用户自备 key 的 OMDb，或 IMDb 官方公开数据集 `datasets.imdbws.com`——实测可访问，但那是全量 TSV，形态完全不同）。这一点在动手分发之前需要单独决定。

</details>

<details>
<summary><b>接口再变时怎么排查</b>（两套诊断工具）</summary>

上面的结论就是靠这两个工具跑出来的，它们都留在仓库里，**跑在你自己的机器上**：

```bash
node scripts/imdb-probe.mjs              # 本机探测：一次打完所有候选路径
node scripts/imdb-probe.mjs --self-test  # 不联网，先验证脚本自己的判读逻辑
node scripts/imdb-probe.mjs --curl       # 不发请求，只打印等价的 curl 命令
```

零依赖，不用 `npm install`、不用先 build，Node 18+ 直接跑。它会依次测：

| 组 | 测什么 |
| --- | --- |
| 0 · 连通性 | 六个域名分别是「连不上 / 连得上但被拒 / 正常」——**三态**，中间那档最容易被误读成接口挂了 |
| 1 · 检索入口 | 7 条候选 × 4 种片名，并逐个确认 `parse.ts` 依赖的 `l`/`y`/`qid` 字段在不在 |
| 2 · 取分路径 | GraphQL、条目页 JSON-LD、`__NEXT_DATA__`、`/ratings/` 页、移动版，附带体积和耗时 |
| 2b · 深挖 | 仅在取分全败时触发：换六种身份重试，并识别反爬拦截页 |
| 3 · 请求头敏感性 | 同一接口换四种头，其中包括 `Origin: chrome-extension://…`——**扩展的真实形态** |
| 4 · 官方数据集 | `datasets.imdbws.com`，唯一一条有正式条款的路 |
| 5 · 端到端 | `--title "片名"` 时走一遍检索 → 取分 |

**Windows 用户注意**（脚本已针对性处理）：

- 中文 Windows 的 cmd 默认代码页是 936，Node 输出 UTF-8 会显示成乱码。先 `chcp 65001` 或改用 Windows Terminal。**乱码只影响终端显示**，`probe-out/` 里的报告始终是正常的 UTF-8。
- `--curl` 会自动按平台生成：Windows 上用 `curl.exe`（PowerShell 里 `curl` 是 `Invoke-WebRequest` 的别名）、双引号、`^` 续行、`findstr` 代替 `grep`。POST 的请求体一律写成文件用 `-d @` 引用，不内联进命令行——JSON 里本来就有双引号，内联后在 cmd 里会被 MSVCRT 的参数规则拆散，在 PowerShell 里 `$` 又会被当变量展开。

两个容易踩的坑，脚本会主动提醒：

- **Node 的内置 fetch 默认不读 `HTTPS_PROXY`**（浏览器和 curl 会读）。所以「浏览器能打开 imdb.com，但脚本全红」完全可能，那不代表接口挂了。用代理时要 `NODE_USE_ENV_PROXY=1 node scripts/imdb-probe.mjs`。
- **`--self-test` 值得先跑一次。** 这个脚本写于一个所有 IMDb 域名都被拒的环境，它的判读逻辑从没跑过成功分支；万一有 bug，跑出来会是「接口全红」这个假阴性，把排查带偏。

另一个入口是扩展弹窗里的**「检索接口诊断 → 运行 IMDb 诊断」**，它跑在浏览器里，请求由 Chrome 自己发出。**两者不一致时以浏览器那份为准**——扩展最终跑在那个环境里。

这次的取分方案正是这么定下来的：Node 那轮六条路全败，一度以为 IMDb 整体封了；浏览器那轮里「GraphQL + 自定义头」直接 200。Node 补不出真实的 TLS 指纹和 HTTP/2 帧序，被拦是它自己的问题，不是接口的问题。

</details>

<details>
<summary><b>配额治理</b>（视口过滤、驻留判定、退避跨重启、点击优先级）</summary>

**匿名请求的配额很紧，每个请求都很珍贵。** 实测同一组查询词几分钟前还能全部命中，反复请求之后就整体落空。所以整个设计围绕「省配额」展开：

- **只为真正停下来看的卡片发请求。** 先按视口过滤（首页能渲染几百张卡片，用户只看得到十几张），再加 600ms 驻留判定——快速滚动时大量卡片一闪而过，一进入视口就排队的话，配额全花在用户根本没看的封面上。掠过的卡片不 unobserve，往回滚还能重新触发。
- **退避状态必须跨 service worker 重启存活。** MV3 的 worker 闲置约 30 秒就被回收，退避记录若只在内存里就会归零，用户每次停顿后再滚动都会在对方仍限流时立刻重新开打，把限流越打越深。现在落盘在 `chrome.storage.local`，存的是恢复时刻的绝对时间戳，重启后按剩余时长恢复，继续被限流时从当前深度接着翻倍。
- **把配额优先花在用户点开的片上。** 点击是页面上最强的兴趣信号，而在此之前扩展对「主动点开的片」和「随手划过的片」一视同仁——同一个队列、同样的「未收录」TTL，这在紧配额下是明显的错配。现在点击会被记进 `chrome.storage.local`：该片的查询插到队首（同档内仍是先来先服务），并且允许绕过一条**写在点击之前**的「未收录」缓存重查一次。重查后无论结果如何都会重写缓存，绕过随即自动失效；加上 30 分钟的点击冷却，同一部片不会被反复重查。兴趣的键只用「归一化标题 + 季数」，刻意不含年份和类型——列表卡片上拿不到这两项，用完整的缓存键会让「点卡片」和「弹层查询」落在不同的键上，信号等于白记。
- 同一标题的并发查询去重；命中结果缓存 7 天、未命中缓存 12 小时。
- 出网请求全部经由限速队列，识别到 403/429 或风控页就进入指数退避——风控页返回的是 200，只看状态码会把它当成正常响应，所以要同时看响应内容和最终跳转地址。

**宁可不显示，也不显示错的分数。** 标题匹配走归一化（全半角、繁简、变音符号、标点、季数后缀）加候选打分，年份和类型作为消歧信号。有年份时阈值 70 分，没年份时收紧到 88 分——列表卡片上通常拿不到年份，此时仅仅是「标题包含关系」不足以判定为同一部片。把《蝙蝠侠》配到《蝙蝠侠归来》比留空更糟。

</details>

<details>
<summary><b>接 Prime Video：为什么选择器认的是路由而不是 class</b></summary>

Netflix 和 Prime Video 只有 DOM 知识不同 —— 观察器、驻留判定、角标渲染、点击记兴趣、卡片复用检测这一整套完全一样，而且是这个项目里踩坑最多的部分（分数挂错封面、角标跨挂载点重复、点角标被误记成兴趣，每一条都真实发生过）。所以这些抽进了 `src/content/site.ts`，站点只提供一个 `SiteAdapter`：一组选择器 + 怎么从 DOM 里读出片名。Netflix 的入口文件因此从 362 行缩到 26 行，行为一字未改（原有 333 个用例全绿）。

**选择器已按线上实测结构收敛。** 第一版是照推测写的，实测暴露出它把 181 个链接都当成了影片卡片 —— 其中包含播放按钮（扩展真的拿「Watch now」去查了评分）和 aria-hidden 的重复链接。现在改成三层：站点自己的卡片标记（`data-testid="poster-link"`、`data-card-title`）优先，路由契约兜底并排除掉那些「长得像卡片的东西」。 开发环境访问不了 primevideo.com（网络策略拒绝），而且列表页要登录、按区域渲染，抓不到真实 DOM。这个项目为「凭记忆写选择器」付过一次代价：v0.1 的 Netflix 选择器单测全绿、线上零命中。所以这一份换了条路：

**优先挂在路由契约上，而不是样式上。** 影片卡片一律通过 `href` 里的 `/detail/<ASIN>` 来认。理由是稳定性有量级差别：

| 依据 | 稳定性 |
| --- | --- |
| CSS-in-JS 的哈希 class（`_1x_1`） | 每次构建都变，依赖它等于埋雷 |
| `data-testid` / `data-automation-id` | 比 class 稳，但仍是内部约定，会重命名 |
| **`/detail/<ASIN>` 路由** | 产品对用户的契约，变了等于站点大改版 |

同一条判断也用在了「哪些 `<a>` 不是影片」上：页面上大量链接是分类、账号、帮助，路由过滤把它们挡在外面 —— 在豆瓣那种紧配额下，这比什么都重要。

详情页那边多一道门禁：Prime Video 的详情是**整页跳转**而不是弹层，所以 `extractFromDetail` 先用 URL 判断当前是不是 `/detail/` 页，不是就返回 null。少了这道门禁，每次打开首页都会拿那个 `h1`（多半是「Prime Video」或某个分类名）去查一次评分。

**怎么收敛这份选择器**：在 Prime Video 的列表页打开 Console，把 `scripts/dom-probe.js` 整个粘进去回车。它不是「检查我猜的选择器对不对」，而是**从零发现结构** —— 先按链接地址找出影片卡片，再把卡片自身、上溯四层祖先、封面图、以及所有 `data-*` 钩子摊开。把报告贴回来即可据实改写选择器。

</details>

<details>
<summary><b>Netflix 改版了怎么办</b></summary>

Netflix 是没有公开契约的商业站点。所有 DOM 知识都集中在 `src/content/netflix/selectors.ts`，每个位置都给了一组候选选择器并按顺序尝试，改版时只需要动这一个文件。

**只认 `data-uia`，不碰 class。** Netflix 现在的 class 全是 CSS-in-JS 生成的哈希名（`default-ltr-iqcdef-cache-19c3xp8` 这种），每次构建都会变，依赖它们等于埋雷。`data-uia` 是 Netflix 自己的测试钩子，稳定得多。影片卡片是 `a[data-uia="standard-card"]`，标题在同一个元素的 `aria-label` 上。

**卡片类型要逐个列举，不能用通配。** 同一批 `*-card` 里还混着 `cloud-game-card`（云游戏），拿游戏名去查评分既查不到又白费配额。

测试用的 fixture 是从线上直接抓下来的真实 HTML，不是照着记忆写的。这一点是有教训的：第一版的选择器凭记忆编写，单测全绿，线上却一张卡片都匹配不到——**适配器这类代码，fixture 的真实性比用例数量重要得多**。

内容脚本带了自检：打开页面 8 秒后若一张卡片都没找到，会在 Console 打出一条警告。

构建版本戳也是这一轮的产物：排查时反复踩同一个坑——`git pull` 不会自动重建，重建后还要去扩展页点刷新，少做一步和「代码有 bug」在表现上完全一样。**改动无法生效时，先证明新代码真的在跑，再去怀疑逻辑。**

</details>

<details>
<summary><b>和其它扩展共存</b></summary>

角标声明了 `translate="no"` 和 `notranslate`，CSS 里还有一条兜底规则把角标内部的任何外来元素隐藏掉。这不是过度设计：实测「沉浸式翻译」会把角标里的「豆」字当成待翻译文本，译成「豆子」再把译文包在 `<font>` 里插进角标内部，渲染出来就是「豆 豆子 8.4」。

注意那条 CSS 规则的层级：角标的直接子元素是 `.dbr-part`，logo 和分数在第二层。加来源时若忘了同步，新那一段会被整段隐藏，而且没有任何报错——所以有一条专门盯这个层级的用例。

这类问题在本地开发时完全看不到——开发环境没装那些扩展。用户报告显示异常时，让他们把 `document.querySelectorAll('.dbr-badge')` 的 `outerHTML` 贴回来，比任何猜测都快：这次就是靠这份 dump 一眼看到了 `immersive-translate-target-wrapper`，而在那之前已经沿着「重复角标」的错误方向修了两轮。

</details>

<summary><b>开发注意</b></summary>

沙箱化的 CI 环境访问不了 `douban.com`，IMDb 的域名也被网络策略拒绝，所以数据层的测试全部基于 fixture——但 fixture 是**实测抓回来的真实响应**，不是照记忆构造的。真实接口的可用性只能在浏览器里验证。

接口再次失效时，扩展弹窗里有个「检索接口诊断」按钮，打开一个页面自动逐个探测候选接口并打印真实响应，不需要开 DevTools。这个页面（`src/probe/`）是临时脚手架，接口稳定后应当删掉。

它救过四次场：发现 `subject_suggest` 从 `www` 搬到 `movie` 子域；发现完整搜索的软限流被误当成空结果；确认 suggest「返回空数组」是限流表现而非接口死亡；确定 IMDb 的 GraphQL 必须带自定义头。

三条通用教训：

1. **不要凭记忆假设第三方接口的响应形状。**
2. **对没有契约的接口，「空结果」永远可能意味着「被限流」**，把它当成事实缓存之前要三思。
3. **本地脚本跑不通不等于接口不可用。** Node 补不出真实浏览器的 TLS 指纹，被反爬拦下是常态——结论要在真实运行环境里取。

</details>
