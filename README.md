# 豆瓣评分 for Netflix

**v0.2.0** · 一个 Chrome 扩展：在 Netflix 的影片封面上就地显示豆瓣评分，点击角标跳转豆瓣条目。交互形态参考 IMDb Ratings for Netflix。

```
┌─────────────────┐
│ 豆 9.2          │  ← 封面左上角的角标，点击跳转豆瓣
│                 │
│   BREAKING BAD  │
└─────────────────┘
```

## 它能做什么

- **列表页封面上直接显示豆瓣评分**，按分数分档配色（8 分以上绿、6.5 以上黄、更低红）
- **鼠标悬停出的详情弹层里也显示**，那里能拿到年份，匹配更准
- **点角标跳转豆瓣条目**，不会误触发 Netflix 的播放
- **界面语言无所谓** —— 英文原名、简体译名、繁体台译都能命中同一部片
- **宁可不显示，也不显示错的分数**：匹配不够可信时留空，而不是给一个看起来对的错分

## 安装

目前是开发版，需要自行构建：

```bash
npm install
npm run build
```

然后在 Chrome 打开 `chrome://extensions` → 打开右上角的**开发者模式** → 点**「加载已解压的扩展程序」** → 选择项目下的 `dist` 目录。

> **改代码后要三步**：`npm run build` → 在 `chrome://extensions` 点该扩展的 🔄 刷新 → 刷新 Netflix 页面。少做一步和「代码有 bug」的表现完全一样，参见下方「先确认跑的是哪一版」。

## 使用与设置

点浏览器工具栏上的扩展图标，可以调整：

| 设置 | 说明 |
| --- | --- |
| 启用扩展 | 总开关。关掉后立即清除页面上所有角标 |
| 在列表封面上显示 | 关掉则只在详情弹层里显示 |
| 在详情弹层中显示 | 悬停卡片弹出的详情层 |
| 豆瓣未收录时也占位 | 默认关闭，列表页留白更干净 |
| 角标位置 | 封面的四个角任选 |
| 清空评分缓存 | 想强制重新查询时用 |

弹窗底部还会显示已缓存的条数、已记录的「关注」部数；被豆瓣限流时会变成橙色提示并给出恢复时间。

## 使用体验的两个预期

**首次浏览新页面时，会有一部分卡片没有评分。** 这不是 bug，是刻意的设计取舍：扩展以匿名方式访问豆瓣（不携带 cookie，见「隐私」一节），而豆瓣对匿名请求的配额很紧。所以请求经过严格限速，只为你真正停下来看的卡片查询。**已查到的会缓存 7 天，常看的内容会越来越全。**

**评分是陆续出现的，不是一次性刷出来。** 视口里的卡片按从上到下、从左到右的顺序排队查询，间隔 2.5 秒。

**想先看哪部，点它一下。** 点开卡片就是在告诉扩展「我对这部感兴趣」：它的查询会插到队首优先出分；如果它此前显示的是「未收录」，还会重新查一次 —— 那多半只是当时被豆瓣限流了。同一部片半小时内只会因此重查一次，连点几下不会多花配额。这个记录只存在本地（最多 200 部），不上传任何地方。

## 遇到问题

| 现象 | 怎么办 |
| --- | --- |
| 完全没有角标 | 先确认跑的是哪一版（见下）；再看 Console 有没有「没有找到任何影片卡片」的警告 —— 那说明 Netflix 改版了 |
| 只有少数片有评分 | 正常，见上方「使用体验的两个预期」。等缓存积累 |
| 角标里出现奇怪的文字 | 多半是别的扩展（如翻译类）在改 DOM，见「和其它扩展共存」 |
| 评分明显配错了片 | 这是真 bug。点扩展图标 →「检索接口诊断」→ 用页面下方的「单片排查」输入片名，把输出发给开发者 |
| 弹窗显示橙色限流提示 | 等提示里给出的时间，期间扩展会自动停止请求 |

**先确认跑的是哪一版。** `npm run build` 会打印一个版本戳，内容脚本把同一个戳写在 `<html data-dbr-loaded>` 上。在 Netflix 页面的 Console 里执行 `document.documentElement.dataset.dbrLoaded`，两者一致才说明新代码真的生效了。

想看详细日志：Console 里执行 `localStorage.setItem('dbr:debug', '1')` 后刷新页面。

## v0.2.0 有什么

第一个真正可用的版本。v0.1 完成了架构搭建，但三条外部依赖全部与实际不符，v0.2 逐一实测校正：

- **Netflix 选择器整体重写。** v0.1 的选择器凭记忆编写，线上一张卡片都匹配不到 —— Netflix 已换掉整套 DOM。现在只认 `data-uia` 测试钩子，不碰 CSS-in-JS 生成的哈希 class。
- **豆瓣取数路径三次修正。** 原接口下线 → 换域名 → 误判为失效而整个切走 → 最终定为「suggest 为主 + 完整搜索兜底」的两级方案。关键教训：对没有契约的接口，**「空结果」永远可能意味着「被限流」**。
- **配额治理。** 退避状态跨 service worker 重启存活、驻留判定、缓存版本化自动失效 —— 都是为了在紧配额下让每个请求不白费。
- **和翻译类扩展共存。** 角标声明 `translate="no"`，防止译文被插进角标内部。

完整的技术决策与踩坑记录见下文各节。

## 它是怎么工作的

```
内容脚本 (Netflix 页面内)              background service worker
┌────────────────────────────┐        ┌──────────────────────────────┐
│ MutationObserver           │        │ RequestQueue                 │
│   发现新出现的影片卡片      │        │   串行 + 限速 + 指数退避      │
│ IntersectionObserver       │        │ DoubanClient                 │
│   只为进入视口的卡片查询    │──消息─→│   suggest 为主，完整搜索兜底  │
│ badge                      │←──────│ matcher                      │
│   注入角标 / 复用时刷新     │        │   候选打分，不够可信就不显示  │
└────────────────────────────┘        │ RatingCache                  │
                                      │   storage.local，命中缓存 7 天│
                                      └──────────────────────────────┘
```

### 三个关键设计

**豆瓣没有公开 API。** 官方 API v2 早已停发 key，走的是豆瓣站内在用的两个检索入口，主备关系（均实测）：

- **主：`movie.douban.com/j/subject_suggest`。** 轻（几百字节）、带年份和原名（`sub_title` 存原始语言标题）、简体和英文都能查。它的限流表现是**返回空数组而不是报错** —— 这曾让我们误判它「彻底废了」而整个切走，其实它只是当时被限流了。繁体查不到，靠上层先做繁转简。
- **备：`search.douban.com/movie/subject_search`。** 解析结果页内嵌的 `window.__DATA__`。召回宽得多（会搜「又名」，港台译名靠它）且自带评分，但对无 cookie 访问的限流极严，几次就触发软限流：**HTTP 200 + `error_info:"搜索访问太频繁。"` + items 为空**。这个形态曾被当成有效的空结果缓存成「未收录」，导致整页所有片子（包括绝命毒师）显示未收录 —— 所以 `error_info` 非空必须按限流处理，绝不能当成"豆瓣没这部片"，并且该接口只在 suggest 拿不到可信匹配时才出场，软限流后自我静默 5 分钟且不牵连 suggest。

suggest 不带评分，命中后由 `subject_abstract` 补一次；完整搜索的结果自带评分则免掉这一步。这些接口都没有契约保证，解析一律「宽进严出」；切 `__DATA__` 用括号配对扫描而不是正则。

**不解析条目页 HTML。** 曾打算拿 `movie.douban.com/subject/<id>/` 做取分兜底，实测第一次请求就被重定向到 `sec.douban.com` 的风控页。这条路不但取不到分，还会白白把请求队列打进退避、连累后续正常请求，所以整个移除了。搜索结果页反而不受这个限制。

**匿名请求的配额很紧，每个请求都很珍贵。** 实测同一组查询词几分钟前还能全部命中，反复请求之后就整体落空 —— suggest 返回空数组、完整搜索返回 `error_info`「搜索访问太频繁」。所以整个设计围绕「省配额」展开：

- **只为真正停下来看的卡片发请求。** 先按视口过滤（首页能渲染几百张卡片，用户只看得到十几张），再加 600ms 驻留判定 —— 快速滚动时大量卡片一闪而过，一进入视口就排队的话，配额全花在用户根本没看的封面上。掠过的卡片不 unobserve，往回滚还能重新触发。
- **退避状态必须跨 service worker 重启存活。** MV3 的 worker 闲置约 30 秒就被回收，退避记录若只在内存里就会归零，用户每次停顿后再滚动都会在豆瓣仍限流时立刻重新开打，把限流越打越深。现在落盘在 `chrome.storage.local`，存的是恢复时刻的绝对时间戳，重启后按剩余时长恢复，继续被限流时从当前深度接着翻倍。
- **把配额优先花在用户点开的片上。** 点击是页面上最强的兴趣信号，而在此之前扩展对「主动点开的片」和「随手划过的片」一视同仁 —— 同一个队列、同样的「未收录」TTL，这在紧配额下是明显的错配。现在点击会被记进 `chrome.storage.local`：该片的查询插到队首（同档内仍是先来先服务），并且允许绕过一条**写在点击之前**的「未收录」缓存重查一次。重查后无论结果如何都会重写缓存，绕过随即自动失效；加上 30 分钟的点击冷却，同一部片不会被反复重查。兴趣的键只用「归一化标题 + 季数」，刻意不含年份和类型 —— 列表卡片上拿不到这两项，用完整的缓存键会让「点卡片」和「弹层查询」落在不同的键上，信号等于白记。
- 同一标题的并发查询去重；命中结果缓存 7 天、未命中缓存 12 小时。
- 出网请求全部经由一个并发为 1、间隔 2.5 秒的队列，识别到 403/429 或豆瓣的验证页就进入指数退避 —— 风控页返回的是 200，只看状态码会把它当成正常响应，所以要同时看响应内容和最终跳转地址。

**界面语言用哪种都行。** 换到完整搜索之后，英文原名、简体译名、繁体台译都能命中同一部片，不需要为了匹配率去改 Netflix 的语言设置。搜索结果的标题常常是「中文名 原名」拼在一起（`星河战队 Starship Troopers`），解析时会拆成两个名字分别参与匹配 —— 不拆的话英文查询只能算「包含关系」，分数过不了无年份时的阈值。

**宁可不显示，也不显示错的分数。** 标题匹配走归一化（全半角、繁简、变音符号、标点、季数后缀）加候选打分，年份和类型作为消歧信号。有年份时阈值 70 分，没年份时收紧到 88 分 —— 列表卡片上通常拿不到年份，此时仅仅是「标题包含关系」不足以判定为同一部片。把「蝙蝠侠」配到「蝙蝠侠归来」比留空更糟。

## Netflix 改版了怎么办

Netflix 是没有公开契约的商业站点。所有 DOM 知识都集中在 `src/content/netflix/selectors.ts`，每个位置都给了一组候选选择器并按顺序尝试，改版时只需要动这一个文件。

**只认 `data-uia`，不碰 class。** Netflix 现在的 class 全是 CSS-in-JS 生成的哈希名（`default-ltr-iqcdef-cache-19c3xp8` 这种），每次构建都会变，依赖它们等于埋雷。`data-uia` 是 Netflix 自己的测试钩子，稳定得多。影片卡片是 `a[data-uia="standard-card"]`，标题在同一个元素的 `aria-label` 上。

**卡片类型要逐个列举，不能用通配。** 同一批 `*-card` 里还混着 `cloud-game-card`（云游戏），拿游戏名去查豆瓣既查不到又白费请求配额，所以选择器里只写明确要的那几种。

测试用的 fixture 是从线上直接抓下来的真实 HTML，不是照着记忆写的。这一点是有教训的：第一版的选择器凭记忆编写，单测全绿，线上却一张卡片都匹配不到 —— 适配器这类代码，fixture 的真实性比用例数量重要得多。

内容脚本带了自检：打开页面 8 秒后若一张卡片都没找到，会在 Console 打出一条警告 —— Netflix 改版时这是最快的线索。

构建版本戳（见上方「遇到问题」）也是这一轮的产物：排查时反复踩同一个坑 —— `git pull` 不会自动重建，重建后还要去扩展页点刷新，少做一步和「代码有 bug」在表现上完全一样，为此白白多绕了几轮。**改动无法生效时，先证明新代码真的在跑，再去怀疑逻辑。**

## 和其它扩展共存

角标声明了 `translate="no"` 和 `notranslate`，CSS 里还有一条兜底规则把角标内部的任何外来元素隐藏掉。这不是过度设计：实测「沉浸式翻译」会把角标里的「豆」字当成待翻译文本，译成「豆子」再把译文包在 `<font>` 里插进角标内部，渲染出来就是「豆 豆子 8.4」。

这类问题在本地开发时完全看不到 —— 开发环境没装那些扩展。用户报告显示异常时，让他们把 `document.querySelectorAll('.dbr-badge')` 的 `outerHTML` 贴回来，比任何猜测都快：这次就是靠这份 dump 一眼看到了 `immersive-translate-target-wrapper`，而在那之前已经沿着「重复角标」的错误方向修了两轮。

## 隐私

扩展只做两件涉及网络的事：把影片标题发给豆瓣做检索、取回评分。没有任何数据上报到第三方，评分缓存只存在浏览器本地的 `chrome.storage.local` 里。

**「点击过哪些片」也只存在本地。** 记录的是归一化后的标题和一个时间戳，最多 200 条，只用来决定查询的先后顺序，不随请求发往豆瓣、也不上传到任何地方。在弹窗里关掉扩展总开关即不再记录。

**请求不携带 cookie（`credentials: 'omit'`），这是一个明确权衡后的选择。** 带上浏览器里的豆瓣 cookie（哪怕只是访问过豆瓣被种下的匿名 bid，无需登录）能与正常浏览共享宽松得多的配额，同类插件多数如此；但那等于让扩展以用户身份访问豆瓣。这里选择保持匿名，代价是配额紧、首次浏览新页面时会有相当一部分卡片没有评分 —— 靠 7 天缓存慢慢积累，常看的内容会越来越全。

权限只申请了两项：`storage`（存设置和缓存），以及 `search.douban.com` 和 `movie.douban.com` 两个域名的访问权。

## 已知限制

- 列表卡片上拿不到年份时匹配走收紧后的阈值（88 分）。suggest 的候选带年份，可参与消歧；详情弹层还能提供查询侧年份，阈值放宽到 70。
- 匿名请求的配额很紧，首次浏览一个新页面时会有相当一部分卡片没有评分，需要靠缓存逐步积累。这是「不携带 cookie」这一隐私选择的直接代价，见上方隐私一节。
- 匹配依赖豆瓣的检索结果，冷门片、Netflix 独占的小语种内容可能查不到，此时列表页留空、详情页显示「未收录」。
- 繁简转换用的是一份覆盖影视标题高频字的精简表（见 `src/shared/text.ts`），不是完整的 OpenCC。缺字只会导致匹配不上，不会匹配错；需要时往表里加即可，单测会校验表的结构。
- 剧集按季匹配：查询没有指明季数时默认取第一季，因为用户在列表里看到的就是这部剧本身。
- 尚未支持 Prime Video。

## 开发注意

沙箱化的 CI 环境无法访问 `douban.com`，所以数据层的测试全部基于 fixture，fixture 按线上实测的响应形状构造。真实接口的可用性只能在浏览器里手工验证 —— `www` 下的 suggest 接口变成 404、条目页被风控拦截，这两件事都是靠实际跑一遍才发现的，光看单测全绿并不能说明取数链路还活着。

接口再次失效时，扩展弹窗里有个「检索接口诊断」按钮，打开一个页面自动逐个探测候选接口并打印真实响应，不需要开 DevTools。这个页面（`src/probe/`）是临时脚手架，接口稳定后应当删掉。

它救过三次场：发现 `subject_suggest` 从 `www` 搬到 `movie` 子域；发现完整搜索的「`error_info`: 搜索访问太频繁」软限流被误当成空结果；确认 suggest「返回空数组」是限流表现而非接口死亡。两条通用教训：**不要凭记忆假设第三方接口的响应形状**（`sub_title` 字段被假设了很久才实证），以及**对没有契约的接口，「空结果」永远可能意味着「被限流」**，把它当成事实缓存之前要三思。
